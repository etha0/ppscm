# 부조뱅크 SCM 개발 및 실행

Servlet + JSP/JSTL 기반의 단일 Maven WAR 프로젝트입니다. 계정 권한에 따라 관리 화면과 매장 화면을 분리하며 MariaDB에 데이터를 저장합니다.

## 실행

빌드: JDK 17, Maven 3.9. 결과 클래스: Java 8 호환. 실행: javax.servlet 기반 Tomcat 8.5/9.

```powershell
$env:JAVA_HOME = 'C:\DevTools\java\openlogic-openjdk-17.0.14+7-windows-x64'
& C:\DevTools\apache-maven-3.9.16\bin\mvn.cmd -B package
powershell -ExecutionPolicy Bypass -File scripts/start-preview.ps1
```

접속: http://localhost:8087/scm/app/login

종료: `powershell -ExecutionPolicy Bypass -File scripts/stop-preview.ps1`

WAR 내부 DB 설정은 `src/main/resources/application-dev.properties`와 `application-prod.properties`로 구분하고, `application.properties`에는 공통 설정을 둡니다. 선택한 환경 파일과 공통 설정이 WAR의 `WEB-INF/classes/`에 포함됩니다. 실제 비밀번호를 입력한 파일은 Git에 커밋하지 마세요. 개발 환경의 접속정보는 Git 제외 대상인 `.local/scm.properties`에 보관하며 실행 스크립트가 `SCM_CONFIG`로 지정합니다. 설정 우선순위는 `SCM_DB_URL`, `SCM_DB_USER`, `SCM_DB_PASSWORD` 환경변수 > `SCM_CONFIG` 외부 파일 > WAR 내부 환경별 설정 > 공통 설정입니다.

초기 관리자 아이디는 `admin`입니다. 생성한 임시 비밀번호는 `.local/initial-admin.txt`에서 확인하고 로그인 후 **비밀번호 변경** 메뉴에서 변경하세요. DB 접속 계정과 웹 로그인 계정은 별개입니다.

## 첫 사용 순서

1. 관리자 로그인 후 비밀번호를 변경합니다.
2. 매장을 등록합니다.
3. 매장 사용자를 만들고 소속 매장과 발주/조회 권한을 선택합니다.
4. 카테고리 관리에서 분류를 등록한 뒤 상품 등록 시 선택하고, 입고 관리에서 재고를 입력합니다.
5. 필요한 경우 매장별 가격을 설정합니다.
6. 매장 사용자로 로그인해 상품을 발주합니다.
7. 관리자 수주/출고 화면에서 출고합니다. 일부 상품 또는 수량만 출고할 수 있습니다.

업무 데이터는 빈 상태로 시작합니다. 관리자나 매장에 샘플 거래가 자동으로 추가되지 않습니다.

## 권한

| 권한 | 기능 |
| --- | --- |
| SUPER | 모든 관리 기능, 관리자 계정 생성/수정 |
| ADMIN | 상품·매장·매장 사용자·가격·입출고·재고·통계 관리 |
| STORE_ORDER | 소속 매장 가격 조회, 발주, 미출고 발주 취소, 자기 매장 내역 조회 |
| STORE_VIEW | 소속 매장 상품 가격과 발주 내역 조회 |

서버에서 페이지 접근, 저장 요청, 발주 소유 매장을 검증합니다. 매장 번호나 단가를 브라우저에서 바꿔 보내더라도 계정의 소속 매장과 DB 단가로 발주합니다. 권한 변경/비밀번호 변경 시 세션 버전을 갱신하여 기존 세션을 무효화하고, 계정·매장 사용 상태를 매 요청에 확인합니다. 운영 관리자는 관리자 계정을 수정할 수 없습니다.

비밀번호는 개별 salt와 PBKDF2-HMAC-SHA256 600,000회로 해시합니다. 최소 12자, 최대 128자입니다. 기준: [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

로그인 실패 5회 시 해당 계정은 15분간 잠깁니다. 관리자 계정 수정 저장으로 잠금을 초기화할 수 있습니다. POST 요청은 세션의 CSRF 토큰을 검사합니다. 저장 요청 토큰은 DB에서 중복 여부를 검사하여 같은 요청의 재처리를 막습니다.

## 데이터 처리 정책

- 금액은 DB DECIMAL 및 Java BigDecimal로 처리합니다. 비율 적용 결과는 소수점 둘째 자리에서 반올림합니다.
- 매장별 가격 설정은 기준 공급가에 할인/할증률을 적용하거나 직접 단가를 입력합니다. 전체 판매 상품 또는 개별 상품에 적용할 수 있습니다.
- 발주 접수 시 상품명·단위·단가를 스냅샷으로 저장합니다. 이후 상품이나 가격 변경이 기존 발주에 영향을 주지 않습니다.
- 발주는 수정할 수 없고, 접수 상태이면서 출고 수량이 0일 때만 취소할 수 있습니다.
- 출고할 때 재고를 차감합니다. 발주 접수 단계에는 재고를 예약/차감하지 않습니다.
- 재고 부족 또는 미출고 수량 초과 시 해당 출고 작업 전체를 롤백합니다. 부분 출고하려면 출고할 수량만 입력합니다.
- 발주 행/상품 행을 잠그고 처리하여 동시 출고 시 초과 출고와 음수 재고를 방지합니다.
- 반품은 원 발주의 출고 수량에서 기존 반품을 제외한 범위 안에서 음수 수량으로 기록합니다. 수령 후 재입고 옵션을 선택한 경우에만 재고를 증가시킵니다.
- 수동 재고 조정은 조회 당시 재고와 현재 재고가 같을 때만 적용합니다. 재고 변동 이력에 변경 전/후·증감·사유·담당자를 기록합니다.
- 상품/매장/계정 수정은 버전 값을 확인하여 다른 사용자의 변경을 조용히 덮어쓰지 않도록 합니다.
- 거래 이력 보존을 위해 상품 판매 중지, 매장/계정 중지를 사용합니다. 물리 삭제 기능은 제공하지 않습니다.
- 오늘 지표는 전체 운영의 오늘 기준입니다. 기간 필터는 하단 집계에 적용합니다. 발주/출고/반품 금액 집계는 발주일 기준의 해당 발주 현재 누계, 입출고 변동 집계는 처리일 기준입니다.

## 파일과 화면

상품 이미지는 JPG/PNG 6장, 각 5MB 이하이며 실제 파일 형식과 크기를 서버에서도 검증합니다. 가로/세로 8000px 및 2400만 화소 이내입니다. 이미지 바이너리를 DB에 저장하고 로그인한 사용자에게 이미지 경로로 제공합니다. 대표 이미지는 첫 번째입니다. 새 이미지 업로드는 기존 전체 교체이며 별도 전체 삭제 옵션이 있습니다.

상품 엑셀은 `.xlsx`, 5MB, 1000행까지 지원합니다. 목록에서 내려받은 양식을 사용합니다. 수식 셀은 거절하고, 오류가 있으면 전체 작업을 저장하지 않습니다. 기존 코드 건너뛰기/갱신을 선택할 수 있으며 재고는 엑셀 상품 갱신으로 바뀌지 않습니다. 재고는 입고/조정 화면에서 관리합니다. XLSX에는 기준 상품 가격이 포함되므로 관리자만 다운로드할 수 있습니다.

모바일 접이식 메뉴, 반응형 카드/폼, 표 내부 가로 스크롤을 적용했습니다. 외부 CDN/상용 UI 없이 공통 CSS와 순수 JavaScript를 사용합니다. 목록 검색과 CSV 다운로드는 현재 조회 목록 기준으로 동작합니다.

## 테스트

일반 단위 테스트는 `mvn test`로 실행합니다. 실제 MariaDB 통합 테스트는 운영/개발 DB를 대상으로 실행하지 않습니다. 별도의 `127.0.0.1:3387/scm_test`만 허용하며 `SCM_CONFIG`를 테스트 전용 파일로 지정한 다음 `mvn -Dscm.integration=true test`를 실행합니다. 테스트는 이 전용 DB의 테이블 데이터를 초기화합니다.

계정 잠금, 타 매장 접근, 조회 전용 저장 차단, 단가 스냅샷, 중복 제출, 부분 출고, 재고 부족 전체 롤백, 반품, 취소, 동시 출고, 재고 충돌, 세션 버전 및 조회 범위를 검사합니다.

- 별도 테스트 DB와 Edge 브라우저에서 매장/사용자/상품 등록, JPG/PNG 이미지 저장, 입고, 매장 단가 설정, 발주, 부분 출고, 반품, 권한 변경 및 세션 무효화 확인.
- XLSX 다운로드→동일 파일 업로드와 중복 상품 건너뛰기 확인.
- HTTP 요청으로 조회 전용 계정의 발주, 타 매장 상세 조회, 매장 계정의 관리자 XLSX 다운로드, 잘못된 CSRF, 비로그인 관리자 화면 접근 차단 확인.
- 360/390/768/1440px에서 대시보드·상품 목록·상품 등록·계정 폼·발주 상세의 문서 가로 넘침 없음. 매장 화면 모바일 시각 확인. 브라우저 JavaScript 예외 없음.
- 서버 테스트 DB: 로컬 MariaDB 11.4. 실제 개발 DB 연결 및 화면 조회: MariaDB 10.9.3.

실제 개발 DB에는 초기 관리자와 빈 업무 테이블만 생성했습니다. 검증용 매장·계정·상품·거래는 별도 테스트 DB에만 있습니다. 정산/세금계산서, 외부 ERP 연동, 배치 작업은 이번 요구 범위에 포함되지 않습니다.

## 카테고리 관리

관리자 메뉴의 **상품 운영 → 카테고리 관리**에서 최고관리자와 운영관리자가 카테고리를 등록/수정할 수 있습니다. 1단계 분류이며 중복 이름은 허용하지 않습니다. 표시 순서는 작은 숫자부터, 같은 숫자에서는 이름 순으로 정렬합니다.

- 상품 등록/수정에서 등록된 카테고리를 선택합니다. 카테고리가 없으면 먼저 카테고리 관리에서 등록하세요.
- 상품 관리·가격·재고 목록과 매장 상품 발주에서 고유 카테고리 ID로 정확히 필터링합니다. 비슷한 이름이나 상품명에 포함된 글자로 혼동하지 않습니다.
- 카테고리명을 수정하면 연결 상품의 표시 이름과 엑셀 다운로드도 새 이름으로 바뀝니다.
- 사용 중지는 새 상품에 지정하거나 다른 상품을 해당 분류로 옮기는 것만 제한합니다. 기존 연결 상품은 조회·판매 가능하며 수정 시 기존 카테고리를 유지할 수 있습니다. 상품 판매 중지는 상품별로 설정합니다.
- 엑셀 업로드는 카테고리 관리에 등록된 이름을 사용합니다. 등록되지 않은 분류가 있으면 전체 작업을 취소합니다. 기존 상품은 중지된 기존 분류를 그대로 유지하여 갱신할 수 있습니다.
- 카테고리는 거래/상품 연결 보존을 위해 물리 삭제 대신 중지를 사용합니다. 중지 상태도 조회 필터에 표시합니다.

### 기존 DB 업그레이드

신규 DB는 `schema.sql`에 카테고리 테이블과 상품 외래 키가 포함되어 있습니다. 기존 DB는 상품을 백업하고 앱을 잠시 중지한 뒤 최신 WAR를 빌드하고 아래 명령을 실행합니다.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/migrate-categories.ps1
```

마이그레이션은 기존 상품의 분류명을 등록하고 `category_id`에 연결합니다. 빈 분류는 `미분류`로 모읍니다. 상품 ID·재고·단가·거래 내역은 유지하며 반복 실행해도 이미 연결된 분류를 덮어쓰지 않습니다. 이전의 문자열 `products.category`는 호환용으로 보존하고, 새 화면과 엑셀에서는 카테고리 마스터 이름을 사용합니다. 마이그레이션에는 테이블 생성/수정 권한이 필요합니다.

현재 개발 DB에는 상품 백업 후 업그레이드를 적용했습니다. 테스트용 카테고리나 상품은 별도의 로컬 테스트 DB에만 등록했습니다.
카테고리 변경 검증: 서버 테스트 18개 통과. 브라우저에서 카테고리 등록/수정, 상품 선택과 정확한 필터, 중지 분류 유지/신규 배정 제한, 매장 권한 차단, 엑셀 왕복 및 360/390/768/1440px 레이아웃 확인. JavaScript 오류 없음.

## 공급업체 관리 및 입고 연결

최고관리자와 운영관리자는 **입출고 · 재고 → 공급업체 관리**에서 업체명, 담당자, 연락처, 주소, 사용 상태를 등록/수정합니다. 업체명은 필수이며 중복을 허용하지 않습니다. 공급업체 등록은 로그인 계정을 생성하지 않으며 매장 계정에서는 이 메뉴에 접근할 수 없습니다.

- 먼저 공급업체를 등록한 뒤 **입고 관리 → 입고 등록**에서 상품과 공급업체를 선택합니다. 사용 중인 공급업체 선택은 필수입니다.
- 사용 중지한 공급업체는 신규 입고 선택에서 제외됩니다. 저장 시점에도 서버에서 상태를 다시 확인합니다.
- 입고 이력에는 공급업체 ID와 입고 당시 업체명을 함께 저장합니다. 이후 업체명 변경이나 사용 중지로 과거 이력이 바뀌지 않습니다. 이력 보존을 위해 삭제 대신 사용 중지를 사용합니다.
- 공급업체가 없는 경우 입고 등록 화면의 공급업체 관리 링크로 이동하여 먼저 등록합니다.

### 기존 DB 업그레이드

신규 DB는 `schema.sql`에 공급업체 테이블과 입고 이력의 외래 키가 포함되어 있습니다. 기존 DB는 앱을 중지하고 `inventory_events`를 백업한 뒤 최신 버전을 빌드하여 다음 명령을 실행하고 앱을 재시작합니다.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/migrate-suppliers.ps1
```

기존 입고의 공급처 문자열에서 앞뒤 공백을 제거한 이름으로 공급업체를 만들고 연결합니다. 입고 이력의 원문은 그대로 보존하며 빈 공급처는 미연결 상태로 유지합니다. 이미 연결된 이력은 반복 실행해도 변경하지 않습니다. 현재 개발 DB에는 백업 후 이 업그레이드를 적용했습니다.

공급업체 변경 검증: 서버 테스트 총 20개 통과. 공급업체 중복/동시 수정 방지, 계정 미생성, 유효한 업체만 입고 허용, 실패 시 재고 롤백, 과거 업체명 보존, 기존 데이터 전환과 재실행을 검사했습니다. 별도 테스트 DB의 Edge 브라우저에서 등록/수정·입고 저장·중지 업체 제외·매장 접근 차단 및 360/390/768/1440px 화면을 확인했습니다.

## 출고 등록 그리드

출고일과 메모 아래에 상품명·단위·발주 수량·기출고·미출고·현재 재고·이번 출고 수량을 표로 표시합니다. 상품별 입력값이 기존 부분 출고 처리에 연결됩니다. 이번 출고 수량의 기본값은 미출고 수량입니다. 출고하지 않는 행은 0으로 변경하며, 미출고 수량과 재고 중 작은 값까지 입력할 수 있습니다. 출고 완료 행은 입력을 잠급니다. 재고가 부족하면 현재 재고 이하로 수량을 줄여야 저장할 수 있으며, 재고가 없는 행은 0으로 변경합니다. 모바일에서는 표 영역만 가로 스크롤합니다.


## 상품별 재고 이력 팝업

재고 관리 상단 목록의 재고 이력 버튼을 누르면 선택한 상품의 이력만 레이어 팝업으로 조회합니다. 상품명·코드·현재 재고와 처리일·등록일·구분·변동·변경 전후 재고·사유·담당자를 표시합니다. 최신 등록 순으로 100건씩 조회하며 이전 이력과 최신 이력 버튼으로 이동합니다. 이력이 없으면 안내 문구를 표시합니다. 관리자만 조회할 수 있으며 하단 최근 재고 변동 이력은 기존대로 유지됩니다. 닫기 버튼, Esc, 바깥 영역 클릭으로 닫을 수 있고 모바일에서는 표 내부를 좌우로 스크롤합니다.


환경 선택은 pom.xml의 Maven 프로필로 합니다. 개발: mvn clean package -Pdev, 운영: mvn clean package -Pprod. 프로필을 생략하면 dev입니다. 결과는 target/scm.war이며 선택한 환경 설정만 포함됩니다. 환경 전환 시 clean 빌드를 권장합니다. SCM_PROFILE 환경변수와 -Dscm.profile JVM 옵션은 더 이상 사용하지 않습니다. DB 환경변수와 SCM_CONFIG 외부 파일의 우선순위는 유지됩니다.
